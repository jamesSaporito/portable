# Running in portable

You're in portable, a Linux microVM (Docker Sandboxes) on the user's Mac. These notes describe how it differs from working on the Mac directly.

- **Files:** only the folder the user started portable in (`$WORKSPACE_DIR`) is shared with the Mac, at the same path. Nothing else on the Mac exists in here, and containers you start see only this folder too. If a task needs files outside it, say so; the user can start portable in a folder higher up.
- **Network:** outbound traffic goes through a proxy on the Mac that allows a list of hosts by name (GitHub, npm, Terraform, Infracost, Docker Hub, the Alpine and Debian mirrors, AWS) and refuses everything else, for you and for the containers you start. A blocked host fails fast ("connection refused", "Permission denied", "Could not connect to server", or a TLS error). Don't work around it with other mirrors, proxies or turned-off checks. Tell the user which host was blocked; they can add it to `PORTABLE_ALLOW_DOMAINS` in portable's `.env`.
- **Credentials:** `GH_TOKEN`, `INFRACOST_CLI_AUTHENTICATION_TOKEN` and Claude's token are placeholders; the proxy puts the real values on requests to GitHub, Infracost and Anthropic. `gh`, `git` to GitHub and `infracost` work as they are; infracost has the Terraform and AWS plugins built in and can't download others. Don't run `gh auth login`, `infracost auth login` or `claude /login` unless the user asks, and don't try to read or move the tokens. AWS credentials are temporary (about an hour); when they expire, ask the user to run `portable` again.
- **Docker:** `docker` and `docker compose` talk to this sandbox's own engine, so images, containers and volumes (databases included) start empty and are separate from the Mac's. A port a container publishes is on `localhost` in here, and portable forwards it to the Mac within a few seconds (TCP, published on all interfaces, the usual `-p 3000:80`; one bound to `127.0.0.1` isn't), at the same number when the Mac has it free and otherwise at the next free one. `/etc/portable/ports` lists each forwarded port as `<sandbox port> <Mac port>`; after starting something, read it (wait up to about 20 seconds for new lines) and give the user the Mac URL, `http://localhost:<Mac port>`. If a port never appears there, tell the user to run `portable ports` on the Mac. Other sessions may share this sandbox and its engine, so leave containers you didn't start alone, and use the `docker-ports` skill before publishing a port.
- **Claude configuration:** `~/claude-configuration` (the user's skills, rules and `CLAUDE.md`, linked into `~/.claude`) is a read-only copy that portable updates from GitHub when the sandbox boots. Don't try to edit it. To change a skill or rule, clone the repo (`git -C ~/claude-configuration remote get-url origin`) into the workspace, make the change there and push a branch or open a PR. Once it's merged, the user runs `./install.sh update` on the Mac, and the next portable boot picks it up in here.
- **Node projects:** `node_modules` in the workspace usually holds the Mac's install, with macOS-only native binaries. When a project runs in Docker, run installs, builds, tests and dev servers through its compose services (e.g. `docker compose run --rm <service> pnpm test`), never `pnpm install`/`npm install` directly against the shared folder: that would swap in Linux binaries and break the project on the Mac. If a project has no compose setup, ask before installing.
